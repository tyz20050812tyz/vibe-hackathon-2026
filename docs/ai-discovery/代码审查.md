### 问题清单

#### 严重问题

**问题 1：画像“负责排序偏好”的核心承诺没有进入普通目录搜索的契约。**

- 位置：`方案设计.md:11-15`、`方案设计.md:149-158`、`方案设计.md:98-111`、`方案设计.md:347-353`。
- 问题：规格将阅读偏好定义为“哪些合格资源更贴近我”的软排序，但 `SearchResourcesQuery`、目录 RPC、`GET /api/resources` 与阶段 B/C 都没有 `sort`/`personalization` 开关、认证输入或排序输出。唯一具体的画像排序算法位于 DiscoveryModule。因此按本文落地后，用户画像只能影响“偏离一点”，不能影响用户主动搜索得到的合格资源顺序。
- 风险：这会直接违反三层职责分工，用户看不到“用户画像负责排序偏好”的主价值；后续临时在客户端排序又会破坏服务端分页、分享 URL 和可解释性。
- 建议：在实施前二选一并写死。推荐方案是给搜索增加显式 `sort=catalog|personalized`（默认 `catalog`），认证用户选择 `personalized` 时由服务端读取画像，对**已满足硬筛选的完整候选集**排序，并返回 `personalization: profile|catalog`；匿名或无画像回退 `catalog`。若产品只希望画像影响 discovery，则应收窄第 1 节的职责表和相关验收表述，避免承诺普通搜索个性化。

**问题 2：搜索 RPC 的“改签名”迁移方案无法直接使用 `CREATE OR REPLACE FUNCTION`，会留下旧重载和权限。**

- 位置：`方案设计.md:98-111`、`方案设计.md:332-334`；现有函数定义位于 `supabase/migrations/202608210001_add_resource_catalog_search.sql:4`。
- 问题：现有函数签名为 `(text, text, text, integer)`，新方案变为七个参数且有数组类型。PostgreSQL 的 `CREATE OR REPLACE FUNCTION` 不能改变输入参数类型或数量，会新建同名重载，而不是替换旧函数。PostgREST/Supabase 通过名称调用 RPC 时将面对同名候选；旧函数的 execute grant 也会继续存在。
- 风险：新 `supabase.rpc("search_resource_catalog", ...)` 可能报“无法选择唯一函数”，或者旧客户端继续绕过新筛选语义；迁移在本地看似成功、部署后 API 不可用。
- 建议：在 migration 中显式 `DROP FUNCTION public.search_resource_catalog(text, text, text, integer)` 后创建新函数，并对新签名执行 revoke/grant；或使用新的函数名并在一次兼容窗口后删除旧 RPC。把旧客户端的兼容策略、切换顺序和 migration 测试写入阶段 A 的完成条件。

#### 建议修改

**问题 3：画像写入的原子性与表级权限边界没有被完整规定。**

- 位置：`方案设计.md:115-125`、`方案设计.md:180-200`。
- 问题：规格要求 `replace_reader_profile` 原子写入，同时又为三张表定义完整的 insert/update/delete RLS 策略，但没有明确数据库 grant 和函数安全模型。若给 `authenticated` 表级写权限，用户可绕过 RPC 直接插入任意 `weight`/`source` 或制造不完整画像，3-8 标签、最多三本和原子替换等不变量不再成立。若不给表级写权限，`DELETE` 的实现也需要专用 RPC 或受控服务层，否则无法完成。
- 建议：将读取与写入分开规定：允许 authenticated 对自身画像 `SELECT`；所有写入只允许 `replace_reader_profile` 和 `clear_reader_profile` 两个 RPC。若采用 `SECURITY DEFINER`，必须固定 `search_path`、不接受用户身份参数、显式检查 `auth.uid()`、撤销 `public` execute 并只 grant authenticated；若采用 `SECURITY INVOKER`，仍须用权限/RLS 阻止表 API 直写并验证函数所需权限。`DELETE` 也应原子删除三表，避免部分删除。

**问题 4：HMAC 上下文 token 被放进 URL，与“不保存匿名浏览路径”的隐私承诺不一致。**

- 位置：`方案设计.md:29-31`、`方案设计.md:204-219`。
- 问题：HMAC 只保证完整性，不提供保密性。紧凑 token 的 payload 包含标签、语言、年份、类型和可读状态，放在详情 URL 后会进入浏览器历史、代理/CDN/应用访问日志以及潜在的 Referer；这实质上形成了匿名筛选路径的可观察记录。
- 建议：明确隐私口径。若允许短期日志，应在非目标中改为“不主动持久化”，并为 URL token 做日志脱敏和 `Referrer-Policy: same-origin`。若不允许暴露筛选内容，改为加密认证 token（而非仅 HMAC），或改用短期服务端上下文 ID；无论哪种方式，都要规定 URL、日志和过期后的清理行为。

**问题 5：公开的 discoveries API 缺少 DeepSeek 成本和滥用控制。**

- 位置：`方案设计.md:221-246`、`方案设计.md:282-304`、`方案设计.md:364-369`。
- 问题：推荐允许匿名访问，且 DeepSeek 在目标选定后由服务端调用；现有约束只有 5 秒超时、输入长度和输出校验，没有按 IP/会话/用户的速率限制、并发上限、每日预算或缓存策略。攻击者可不断更换 `excludeResourceIds` 请求，持续消耗模型额度。
- 建议：把模型开启门禁补为：匿名请求按 IP + 起点限流，登录请求按用户限流；限制全局并发和预算；相同 `(origin, mode, candidate, lens)` 在短 TTL 内复用已校验叙述或模板；限流返回明确的 `429`，但仍可提供不调用模型的模板推荐。只有这些控制验证后，才允许将 Adapter 从默认关闭切为开启。

**问题 6：首次登录问卷从“需要填写”改为可关闭引导，属于产品决策变更，尚未得到确认。**

- 位置：`方案设计.md:25`、`方案设计.md:56-63`。
- 问题：前置需求提出“用户在登录的时候需要填写用户问卷”，本文改为不强制、可关闭，且未完成仍可使用书架和收藏。这是合理的降低流失率方案，但与原始要求不等价。
- 建议：由产品明确选择并记录：a) 登录后必须完成核心问卷才能进入个性化区域；或 b) 当前的非阻塞引导。若采用 b，应把“首次登录问卷”统一改称“首次登录偏好引导”，避免实现和验收方误解为强制流程。

#### 可选优化

**问题 7：亲和度公式是 Dice 系数而非加权 Jaccard，应统一命名。**

- 位置：`方案设计.md:264-280`。
- 问题：`2 * intersection / (target + interests)` 是 Dice coefficient，不是加权 Jaccard。两者的排序行为接近但数值不同，后续埋点、测试数据或文档若称为 Jaccard 会造成误解。
- 建议：将文档和代码统一命名为 `weightedDiceAffinity`，或将公式改为 `intersection / union` 并保留 Jaccard 名称。
