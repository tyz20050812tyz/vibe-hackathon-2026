# 演练数据读写模板

> 目标：验证“前端 -> Next.js API -> Supabase -> 前端”的真实读写闭环。

## 包含什么

| 文件 | 作用 |
| --- | --- |
| `supabase/migrations/20260820_create_demo_records.sql` | 创建演练表和索引 |
| `lib/types/api.ts` | 前后端共享请求与响应类型 |
| `lib/supabase/server.ts` | 服务端 Supabase 客户端 |
| `lib/services/demo-records.ts` | 数据库读写逻辑 |
| `app/api/demo-records/route.ts` | `GET` / `POST` API |
| `app/demo-records/page.tsx` | 演练页面入口 |
| `components/demo-records-template.tsx` | 输入、写入、列表展示 UI |

## 首次使用

1. 打开 Supabase Dashboard -> SQL Editor。
2. 打开并执行 [迁移 SQL](../supabase/migrations/20260820_create_demo_records.sql) 的完整内容。
3. 确认本地 `.env.local` 已有 Supabase 三项变量，Vercel Preview/Production 也已配置。
4. 启动项目：

```bash
npm run dev
```

5. 打开：

```text
http://localhost:3000/demo-records
```

输入一段文字并提交。成功后，它会出现在“最近记录”列表。

若已在补充 `grant` 前执行过迁移，再在 SQL Editor 单独执行：

```sql
grant select, insert, delete on public.demo_records to service_role;
```

该权限只授予服务端的 `service_role`，浏览器仍无法直接访问表。

## API 契约

### 读取记录

```text
GET /api/demo-records
```

成功：

```json
{
  "data": [{ "id": "uuid", "content": "测试", "createdAt": "2026-08-20T00:00:00Z" }],
  "requestId": "uuid"
}
```

### 创建记录

```text
POST /api/demo-records
Content-Type: application/json

{ "content": "测试" }
```

`content` 必填，去除首尾空格后限制为 1 到 500 个字符。错误响应统一为：

```json
{
  "data": null,
  "error": { "code": "VALIDATION_ERROR", "message": "请输入内容。" },
  "requestId": "uuid"
}
```

## 明天如何复用

1. 先复制迁移 SQL，按赛题替换表名、字段和状态。
2. 在 `lib/types/api.ts` 用赛题实体替换 `DemoRecord`。
3. 在 `lib/services/` 写数据库操作，不把 SQL 或 service-role key 放进页面。
4. 在 `app/api/` 校验外部输入，统一返回 `data`、`error`、`requestId`。
5. 前端只依赖 `lib/types/` 的字段；接口未完成前使用同形状 Mock 数据。

## 安全边界

该演练接口没有用户登录，只适合比赛期间的非敏感 Demo 数据。正式功能至少需要补上：

- Supabase Auth；
- 资源归属与权限检查；
- 限流；
- 针对业务表的 RLS policy。

`SUPABASE_SERVICE_ROLE_KEY` 只在 `lib/supabase/server.ts` 和服务端 API 使用，绝不能以 `NEXT_PUBLIC_` 前缀暴露给浏览器。
