# 后端与部署

> 目标：由杨思涵负责快速建立安全、可部署的后端闭环。

## 后端结构

```text
页面 / 组件
    -> app/api/<resource>/route.ts
    -> lib/services/<service>.ts
    -> lib/supabase/
    -> Supabase PostgreSQL
```

- Route Handler：给前端 `fetch`、Webhook 或需要 JSON API 的场景使用。
- Server Action：给当前页面内的简单表单提交使用。
- `lib/services/`：放业务逻辑、LLM 调用和数据库编排。
- 客户端不能读取 service-role key，也不能直接调用需要私钥的第三方接口。

## Supabase 赛前准备

1. 创建 Supabase 项目，将佟雨泽加入成员。
2. 记录项目 URL、publishable key、service-role key。
3. 赛题发布后，先确定表、字段、状态，再运行 SQL。
4. 每张业务表开启 RLS，并只创建必要的访问策略。
5. 保存每次建表或修改表结构的 SQL 到 `supabase/migrations/`。

最小表设计应包含：`id`、必要业务字段、`status`、`created_at`。不要为未确定的功能提前建表。

## API 实现顺序

1. 与佟雨泽先确认 `lib/types/api.ts`。
2. 在 `app/api/<resource>/route.ts` 创建接口。
3. 校验请求参数，再调用 service。
4. 返回统一 JSON；不要把 Supabase 原始错误直接返回给前端。
5. 前端先用同类型 Mock 数据，接口完成后再接真实请求。

推荐安装：

```bash
npm install @supabase/supabase-js zod
```

## Vercel 部署

1. 在 Vercel 导入 GitHub 仓库，框架选择 Next.js。
2. `main` 作为生产分支；功能分支和 PR 自动生成 Preview。
3. 在 Vercel 的 Environment Variables 中配置 `.env.local` 中相同的变量。
4. 每次 Preview 部署后测试一条完整用户路径。

部署出错时依次检查：Vercel Build Logs、本地 `npm run build`、环境变量、Supabase RLS 和 API 返回。
