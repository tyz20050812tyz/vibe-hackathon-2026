## 3. 命名与序列化规则

| 场景 | 规则 | 示例 |
| --- | --- | --- |
| PostgreSQL 表和字段 | `snake_case` | `saved_resources`, `published_year` |
| TypeScript 与 API JSON | `camelCase` | `savedResources`, `publishedYear` |
| URL 资源标识 | 小写 kebab-case slug | `the-library-of-babel` |
| 数据库主键 | UUID | `id` |
| 时间字段 | 数据库存 `timestamptz`，API 返回 ISO 8601 字符串 | `2026-08-21T09:30:00.000Z` |
| 空值 | 不存在或未知的数据使用 `null`，不使用空字符串 | `coverUrl: null` |
| 枚举 | 只用预定义小写字符串，不临时新增 | `availability: "online"` |

数据库字段到 API 字段的映射由 `lib/services/` 负责，页面不得处理 `snake_case`。

## 4. 通用 API 规则

所有接口使用 `lib/types/api.ts` 的统一响应：

```ts
type ApiSuccess<T> = {
  data: T;
  requestId: string;
};

type ApiFailure = {
  data: null;
  error: { code: ApiErrorCode; message: string };
  requestId: string;
};
```

| 情况 | HTTP | 错误码 |
| --- | --- | --- |
| 参数不合法 | 400 | `VALIDATION_ERROR` 或 `INVALID_JSON` |
| 未登录 | 401 | `UNAUTHORIZED` |
| 无权限 | 403 | `FORBIDDEN` |
| 资源不存在 | 404 | `RESOURCE_NOT_FOUND` |
| 重复收藏 | 409 | `ALREADY_SAVED` |
| 服务配置/外部服务失败 | 503 | `CONFIGURATION_ERROR` 或 `SUPABASE_UNAVAILABLE` |
| 其他服务端异常 | 500 | `INTERNAL_ERROR` |

前端不解析 Supabase 原始错误，也不通过错误英文文本判断业务状态。

## 6. 接口标准

| 接口 | 参数 / Body | 成功返回 |
| --- | --- | --- |
| `GET /api/resources` | `q?`, `tag?`, 重复 `language`/`type`/`availability`、`yearFrom?`、`yearTo?`、`sort?`、`limit?` | `SearchResourcesData` |
| `GET /api/resources/[slug]` | path `slug` | `GetResourceData` |
| `GET /api/reader-profile` | Bearer token | `ReadingProfileData` |
| `PUT /api/reader-profile` | `{ interestTagIds, explorationLevel, favoriteBooks?, consent: true }` | `ReadingProfileData` |
| `DELETE /api/reader-profile` | Bearer token | `{ cleared: true }` |
| `POST /api/discoveries` | `{ originResourceId, mode?, excludeResourceIds?, discoveryContext? }` | `DiscoverData` |
| `GET /api/saved-resources` | 无 | `SavedResource[]` |
| `POST /api/saved-resources` | `{ resourceId, note? }` | `SavedResource` |
| `DELETE /api/saved-resources/[resourceId]` | path `resourceId` | `{ resourceId }` |
| `POST /api/auth/sign-up` | `{ email, password }` | `AuthResult` |
| `POST /api/auth/sign-in` | `{ email, password }` | `AuthResult` |
| `POST /api/auth/sign-out` | 无 | `{ signedOut: true }` |
| `POST /api/auth/callback` | `{ accessToken, refreshToken }` | `{ authenticated: true }` |

每个 Route Handler 必须按以下顺序实现：解析输入 -> Zod 校验 -> 身份/归属检查 -> 调用 `lib/services/` -> 转换为 API 类型 -> 返回统一 JSON。

### 6.1 认证接口

`SignUpRequest` 与 `SignInRequest` 都是严格对象 `{ email, password }`：`email` 为规范化的小写邮箱地址；`password` 长度 8 至 72，且必须包含字母、数字与特殊字符。认证接口不返回 access token、refresh token、Supabase 原始用户数据或供应商错误。

```ts
type AuthResult = {
  status: "authenticated" | "confirmation_required";
};
```

- `authenticated`：服务端已通过 HTTP-only Cookie 写入会话，浏览器随后直接访问本项目 API。
- `confirmation_required`：Supabase 已接受注册，需要用户完成验证邮件中的链接后再登录。
- 注册由服务端 `auth.admin.generateLink` 创建用户并签发 Supabase 验证链接；链接仅通过服务器配置的 SMTP 发送。该实现不使用 Supabase Custom SMTP，`SUPABASE_SERVICE_ROLE_KEY`、SMTP 授权码和链接 token 不得进入浏览器或日志。
- `redirectTo` 固定为 `{NEXT_PUBLIC_SITE_URL}/auth/confirmed`，该地址必须在 Supabase Auth Redirect URLs 中允许；完成验证后用户返回个人书架主动登录。
- Supabase 确认链接会以 URL hash 提供短期会话。`/auth/confirmed` 必须立即移除 hash，并只向同源 `/api/auth/callback` 提交会话；该接口验证会话后写入 HTTP-only Cookie。URL hash、access token 与 refresh token 均不得记录、展示或复制。
- 邮箱/密码不匹配或未验证返回 `401 AUTHENTICATION_FAILED`；不以错误信息披露账户是否存在。
- `profiles.display_name` 沿用现有 nullable 约束；首次以有效用户会话访问个人书架时初始化，不新增 Profile 字段。

## 7. 权限规则

- 资源、标签和资源关系是公开可读数据；浏览器仍优先通过 Next.js API 读取，避免页面依赖数据库查询细节。
- `profiles` 和 `saved_resources` 必须开启 RLS。
- 用户只能读取、创建、删除自己的收藏；`saved_resources` 用 `(user_id, resource_id)` 主键防止重复收藏。
- `SUPABASE_SERVICE_ROLE_KEY` 仅限服务端 adapter 使用，绝不进入 Client Component、`NEXT_PUBLIC_` 变量、日志、文档样例或 Git。
- 任何写入用户数据的接口都必须在 API 层验证用户身份，即使数据库已经有 RLS。
- 既有 `/api/profile`、`/api/saved-resources` 与 Auth 流程继续使用服务端 HTTP-only Cookie，页面不得为这些既有接口新增 Bearer 分支。
- 新阅读偏好接口 `GET/PUT/DELETE /api/reader-profile` 必须使用有效 Bearer；`sort=personalized` 的资源搜索和 `POST /api/discoveries` 可选 Bearer，缺失或无效时回退目录排序，不返回认证错误。新功能不得回退到 Cookie 身份。

## 11. 2026-08-26 AI 发现契约增补

本节是本项目 AI 发现模块对前述通用规则的冻结增补；模块详细方案见 [`docs/ai-discovery/方案设计.md`](ai-discovery/方案设计.md)。

### 11.1 认证与领域命名

- `/api/reader-profile` 的 GET、PUT、DELETE 统一要求 `Authorization: Bearer <access token>`；服务端只从 token 派生 `auth.uid()`，不接受 `userId`。公开的 `/api/resources` 个性化排序和 `/api/discoveries` 可选 Bearer；token 无效时回退公共目录。
- 阅读偏好领域统一命名为 `ReadingProfile`，不复用已有个人资料概念 `ReaderProfile`。GET 返回判别式 `{ status: "incomplete", preferences: null }` 或 `{ status: "complete", preferences: ReadingProfile }`。
- 画像写入只能调用 `replace_reader_profile`，清空只能调用 `clear_reader_profile`；两者为 `SECURITY DEFINER` 原子 RPC。`reader_profile_is_complete()` 是画像可用于个性化的唯一判定：存在已完成记录且恰有 3-8 个兴趣标签。三张 `reader_profile*` 表仅允许 authenticated 读取本人，禁止 authenticated/anon 直接写入。

### 11.2 搜索与筛选

`GET /api/resources` 支持 `q`、`tag`、重复键 `language`/`type`/`availability`、闭区间 `yearFrom`/`yearTo`、`sort=catalog|personalized` 和 `limit=1..50`。年份必须为 1000–2100 的整数；`language`、`type`、`availability` 分别最多 3、4、4 个值。同字段多值为 OR，字段之间为 AND；重复值、未知键、非法枚举、年份反转均返回 `400 VALIDATION_ERROR`。`clearSearchFilters` 只保留 `q` 和 `sort`。

### 11.3 Reader Profile 请求与响应

- 阅读偏好领域使用 `ReadingProfile`、`ReadingProfileData`、`ReplaceReadingProfileRequest`，不得修改或复用现有个人资料类型 `ReaderProfile`。
- 未完成画像返回 `{ status: "incomplete", preferences: null }`；完成画像返回 `{ status: "complete", preferences: ReadingProfile }`；清空返回 `{ cleared: true }`。
- PUT 要求 `consent: true`、3–8 个互异标签 UUID、最多 3 本喜爱书目；作者缺失、空字符串或纯空白统一规范化为 `null`。

### 11.4 Discovery Context payload

- `DiscoveryContextPayload` 仅包含 `version: 1`、`originSlug`、规范化结构化硬筛选、`issuedAt`、`expiresAt`，有效期固定为 5 分钟，且至少包含一个结构化硬筛选才可签发。
- payload 严禁包含 `q`、用户 ID、邮箱、ReadingProfile、Bearer token 或喜爱书目；Schema 使用严格对象拒绝任何额外字段。
- 本契约只定义 payload 边界；token 必须由服务端专用方法签发，浏览器不得创建或解密。

迁移顺序固定为 `20260821_create_library_foundation.sql`、`202608210001_add_resource_catalog_search.sql`、`202608260001_add_resource_languages.sql`、`202608260002_create_reader_profiles.sql`、`202608260003_create_resource_catalog_v2.sql`。最后一个 migration 删除旧四参数 `search_resource_catalog(text,text,text,integer)`（可重复执行），再创建 `search_resource_catalog_v2` 与仅 authenticated 可执行的 `search_resource_catalog_personalized_v2`，避免 RPC 同名重载。

### 11.3 发现与隐私

`POST /api/discoveries` 只从 `resource_relations` 选择候选；硬筛选先于画像排序，空候选返回 HTTP 200。带 `discoveryContext` 时使用服务端 AES-256-GCM、5 分钟过期 token，响应必须为 `Cache-Control: private, no-store` 和 `Referrer-Policy: same-origin`；日志只能记录 `present|invalid|expired`，不得记录 token、请求体或完整 URL。搜索资源卡由服务端签发 context 并传入详情链接。

新增错误码为 `INVALID_DISCOVERY_CONTEXT`（400）和 `RATE_LIMITED`（429）。`Resource`/`ResourceListItem` 必须包含 `languages`，列表项包含 `publishedYear`；搜索响应始终返回规范化 `appliedFilters`、实际 `appliedSort` 与 `personalization` 来源。

## 12. 2026-08-27 资源星图契约增补

本节冻结资源星图的共享契约。第一个纵向切片只实现一跳拓扑；二跳的最大 12 个新增节点在后续独立实现。

### 12.1 类型与响应

```ts
type ConstellationDepth = 1 | 2;

type ConstellationNode = {
  resource: ResourceListItem;
  hop: 0 | 1 | 2;
  relationStrength: number | null;
  relationTypes: RelationType[];
  isSaved: boolean;
  affinity: number | null;
};

type ConstellationEdge = {
  id: string;
  sourceResourceId: string;
  targetResourceId: string;
  relationType: RelationType;
  explanation: string;
  strength: number;
  direction: "outbound" | "inbound";
};

type ConstellationData = {
  centerResourceId: string;
  nodes: ConstellationNode[];
  edges: ConstellationEdge[];
  hasMoreSecondHop: boolean;
  personalization: "profile" | "catalog";
};
```

`GET /api/resources/[slug]/constellation?depth=1|2` 使用现有 `ApiSuccess<ConstellationData> | ApiFailure` envelope，所有响应包含 `requestId`。`depth` 缺省为 `1`；非 1/2、重复标量键或未知 query key 返回 `400 VALIDATION_ERROR`。`ConstellationDepth` 和 query Schema 保留 `1 | 2` 以兼容后续二跳，但 2026-08-27 一跳 API 阶段仅启用 `depth=1`：收到合法但尚未启用的 `depth=2` 必须返回 `400 VALIDATION_ERROR`，消息固定为“二跳星图尚未启用，请使用 depth=1。”，不得静默降级或提前返回二跳。资源不存在或不可公开读取返回 `404 RESOURCE_NOT_FOUND`；资源存在但无关系时返回 HTTP 200，仅保留中心节点且 `edges: []`。数据库或配置失败继续使用现有 `SUPABASE_UNAVAILABLE`、`CONFIGURATION_ERROR` 和 `INTERNAL_ERROR`，不新增错误码。

### 12.2 拓扑、方向与排序

- 一跳包含中心资源的全部公开直接入边和出边；中心节点为 `hop: 0`，相邻节点为 `hop: 1`。
- `sourceResourceId` 和 `targetResourceId` 始终保留 `resource_relations` 的原始方向。`direction` 仅表示该边相对当前中心是 `outbound` 还是 `inbound`。
- 相邻资源节点按 resource ID 去重；不同 relation 记录不合并，每个 relation ID 在 `edges` 中最多出现一次。
- 中心节点的 `relationStrength` 为 `null`、`relationTypes` 为空数组；相邻节点的 `relationStrength` 为它与中心所有直接边中的最大强度，`relationTypes` 按 `same_theme`、`contrasting_view`、`historical_context`、`unexpected_bridge` 固定顺序去重。
- `nodes` 稳定排序为 `hop ASC, relationStrength DESC NULLS FIRST, resource.id ASC`；`edges` 稳定排序为 `strength DESC, id ASC`。
- 一跳响应的 `hasMoreSecondHop` 表示是否存在未返回的二跳候选；实现二跳时不得改变一跳节点和边。

### 12.3 认证、个性化与权限

- 接口为公开读，`Authorization: Bearer <access token>` 可选；缺失或无效 Bearer 静默回退公开行为，不返回 401，不回退 Cookie 身份。
- 匿名、无效 Bearer、未完成画像和已完成画像必须返回相同的节点和边拓扑；登录只能影响 `isSaved`、`affinity` 和 `personalization`。
- 无有效完成画像时 `personalization: "catalog"`且所有 `affinity: null`；有效完成画像时为 `personalization: "profile"`。中心节点 `affinity` 固定为 `null`，相邻节点亲和度仅用于视觉提示，不参与拓扑取舍或排序。
- 资源、标签和关系继续遵守现有公开只读 RLS；收藏标记和画像仅通过经 `auth.getUser()` 验证的 Bearer 用户及现有 RLS 读取，不使用 service-role 绕过用户隔离。

### 12.4 数据库索引

`202608270001_add_resource_relation_target_index.sql` 只新增 `resource_relations(target_resource_id, strength DESC)` 索引，用于入边查询；不修改关系字段、RLS、授权或已有数据。执行顺序为已有 relation 基础 migration 和 `202608220001_add_discovery_relation_index.sql` 之后。
