## 1. 技术栈与使用边界

| 层 | 选型 | 为什么采用 | 本项目中的约定 |
| --- | --- | --- | --- |
| Web 框架 | Next.js App Router + React | 页面、服务端渲染、接口与部署在同一工程 | 页面在 `app/`，API 在 `app/api/` |
| 语言 | TypeScript | 在前后端之间提前发现字段不一致 | 共享类型放在 `lib/types/`，不使用 `any` |
| UI | Tailwind CSS + shadcn/ui + Lucide React | 快速搭建一致、响应式的交互界面 | 通用组件在 `components/ui/`，业务组件在 `components/` |
| 业务层 | Route Handlers + Server Actions | 前者供浏览器/第三方调用，后者简化页面内表单写操作 | 不在客户端直接保存服务端密钥 |
| 数据库 | Supabase PostgreSQL | 有托管数据库、认证与行级安全能力 | SQL 由杨思涵维护，必须启用 RLS |
| 部署 | Vercel | GitHub 推送后可自动构建预览与生产版本 | `main` 对应稳定生产部署，PR 对应预览 |

### 1.1 目录边界

```text
app/
  page.tsx                       # 佟雨泽：页面入口
  (product)/                     # 佟雨泽：业务页面与布局
  api/                           # 杨思涵：Route Handlers
components/
  ui/                            # shadcn/ui 基础组件，非必要不直接修改
  ...                            # 佟雨泽：业务 UI 组件
lib/
  types/                         # 共同维护：领域模型与 API 契约
  supabase/                      # 杨思涵：浏览器/服务端 Supabase 客户端
  services/                      # 杨思涵：数据库、LLM、第三方服务封装
docs/                            # 共同维护：题目、决策、接口与验收记录
```

### 1.2 Route Handlers 与 Server Actions 的选择

| 场景 | 采用方式 | 示例 |
| --- | --- | --- |
| 前端 `fetch`、未来移动端、Webhook、需标准 JSON | Route Handler | `POST /api/analyses` |
| 当前页面的表单提交，完成后立即刷新当前页面 | Server Action | 创建一条仅本页面使用的记录 |
| 调用 LLM、使用 service-role key | 仅服务端函数 / Route Handler | `lib/services/ai.ts` 由 API 调用 |

Server Action 也是一个可被请求的服务端入口。它必须验证输入、认证与授权，不能因为按钮只在前端显示就假定请求可信。

## 2. 队友从零启动项目

### 2.1 前置条件

- Node.js：使用项目当前版本或 Node 20+ LTS；本仓库当前验证环境为 Node `24.18.0`。
- npm：使用随 Node 安装的 npm；仓库已有 `package-lock.json`，统一使用 npm，不混用 pnpm/yarn。
- Git、GitHub 账号，并已被加入仓库协作者。
- Supabase 与 Vercel 账号，均建议赛前完成登录并接受项目邀请。

### 2.2 克隆、安装并跑通

```bash
git clone https://github.com/tyz20050812tyz/vibe-hackathon-2026.git
cd vibe-hackathon-2026
npm install
cp .env.example .env.local
npm run dev
```

访问 `http://localhost:3000`。首次加入项目前，必须再运行：

```bash
npm run lint
npm run build
```

验收标准：开发服务器可打开；lint 没有 error；构建完成。当前项目的 Geist 字体通过 Google Fonts 下载，若比赛网络受限，构建可能失败。赛前应替换为本地字体或系统字体，并重新运行 `npm run build` 验证。

### 2.3 环境变量

将 `.env.example` 复制为 `.env.local` 后填写实际值：

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://<project-ref>.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=<Supabase publishable key>
SUPABASE_SERVICE_ROLE_KEY=<仅服务端使用>
LLM_API_KEY=<仅服务端使用>
```

- `NEXT_PUBLIC_` 前缀表示该值会被打进浏览器代码。只能放浏览器安全的 URL 和 publishable key。
- `SUPABASE_SERVICE_ROLE_KEY`、LLM key 不可使用 `NEXT_PUBLIC_` 前缀，且只能在 `app/api/` 或 `lib/services/` 的服务端代码中读取。
- `.env.local` 不提交。`.env.example` 只保留变量名和说明，可提交。

## 3. 后端落地：Supabase + Next.js + Vercel

### 3.1 赛前账号和项目准备

1. 杨思涵创建 Supabase 项目，将佟雨泽邀请为成员；记录项目 URL、publishable key 和 service-role key。
2. 在 Supabase SQL Editor 中执行建表 SQL。每次结构变更把 SQL 保存到 `supabase/migrations/`，并在 PR 描述中说明执行顺序。
3. 开启每张业务表的 Row Level Security (RLS)，策略只授予真实需要的 `select/insert/update/delete` 权限。
4. 在 Vercel 导入 GitHub 仓库，Framework Preset 选 Next.js；Production Branch 保持为 `main`。
5. 在 Vercel Project Settings -> Environment Variables 添加同名变量：生产、预览和开发环境按需要分别配置。服务端密钥只添加到 Vercel，绝不写入仓库。

### 3.2 数据库最小模板

题目发布后不要直接按页面名称建表。先写业务实体、它们的关系和状态流转。例如一个“提交后获得分析结果”的 MVP 可从下面的模板改起：

```sql
create table public.analysis_requests (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references auth.users(id),
  input_text text not null,
  status text not null default 'pending'
    check (status in ('pending', 'processing', 'completed', 'failed')),
  result jsonb,
  error_message text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

alter table public.analysis_requests enable row level security;

create policy "Users can read their own requests"
on public.analysis_requests for select
using (auth.uid() = user_id);

create policy "Users can create their own requests"
on public.analysis_requests for insert
with check (auth.uid() = user_id);
```

无登录的比赛 Demo 也不能因此关闭全部安全策略。可选策略是：通过后端的受控 API 写入，限制字段、频率与总量；或采用匿名认证并按 `auth.uid()` 约束数据。

### 3.3 数据访问分层

```text
React Client Component
        |
        | fetch('/api/analyses') 或调用 Server Action
        v
app/api/analyses/route.ts             # 输入校验、身份权限、HTTP 状态码
        v
lib/services/analysis-service.ts      # 业务编排、LLM 调用、错误映射
        v
lib/supabase/server.ts                # Supabase 查询
        v
Supabase PostgreSQL
```

责任边界：API 不包含复杂业务细节；service 不依赖 HTTP `Request`；页面不包含 service-role key 和 SQL。

### 3.4 Route Handler 的实现步骤

1. 佟雨泽和杨思涵先在 `lib/types/api.ts` 确认请求、成功响应与错误响应类型。
2. 杨思涵在 `app/api/<resource>/route.ts` 实现 HTTP 方法。Route Handler 位于 `app` 内，使用 Web 标准 `Request` / `Response`。
3. 读取 `request.json()` 后先校验字段，再调用 service。无论参数来自浏览器还是 Server Action，均视为不可信。
4. 统一返回 JSON 包装格式，前端不能依赖 Supabase 原始报错文本。
5. 佟雨泽先按契约写 Mock，接口完成后仅替换请求实现，不改变页面数据形状。

推荐安装输入校验库：

```bash
npm install @supabase/supabase-js zod
```

### 3.5 Server Action 使用规则

页面内简单表单可用 `"use server"` 的 Action。适合“创建后回到当前页面”的变更操作；需要稳定 JSON API、流式响应或给多个客户端使用时采用 Route Handler。

每个 Action 都必须：验证输入、检查登录身份和资源归属、限制返回字段；写入成功后用 `revalidatePath` 或相应缓存策略刷新 UI。不要把多个彼此独立的 Action 并行从同一客户端触发，客户端会按顺序派发它们。

### 3.6 Vercel 部署验收

```text
功能分支推送 -> Vercel Preview -> 测试核心流程 -> PR 审查 -> 合并 main
                                                        |
                                                        v
                                                Vercel Production
```

每次部署后检查：主页可访问、关键 API 返回预期状态、环境变量存在、Supabase RLS 没有阻断合法请求、失败状态显示给用户。部署页面错误时先看 Vercel Build Logs，再在本地执行 `npm run build` 复现。

## 4. 双人分工与数据传输契约

### 4.1 人员职责

| 人员 | 角色 | 主责 | 交付物 |
| --- | --- | --- | --- |
| 佟雨泽 | PM1 + 前端 + 测试 | 用户痛点、MVP 范围、信息架构、页面与组件、交互、前端及 E2E 冒烟测试、现场 Demo | 页面路由、组件、Mock、验收清单、演示动线 |
| 杨思涵 | PM2 + 后端 + 测试 | 可行性与数据流、数据库、RLS、Route Handlers、Server Actions、第三方/LLM 集成、部署与接口测试 | SQL、服务层、API、环境变量清单、部署配置 |
| 两人共同 | 产品决策、数据契约、PR 审查、关键路径联调、最终答辩 | PRD、MVP/不做清单、`lib/types/`、种子数据、路演材料 | 可部署的 `main` |

测试不按“前端/后端”割裂：佟雨泽验证用户动作到 UI 结果的完整路径；杨思涵验证 API、数据库约束、权限与异常响应；最终由两人一起过一次真实演示。

### 4.2 必须先确定的 API 标准

赛题发布后 20 分钟内，在 `lib/types/api.ts` 中确定以下内容，修改前须双方确认：

- 资源名与路由：例如 `POST /api/analyses`，命名用复数名词。
- 请求字段：字段名、类型、必填性、最大长度和默认值。
- 成功返回：统一 `data`，避免页面直接读取数据库行。
- 失败返回：统一 `error.code`、用户可读的 `error.message`、用于排查的 `requestId`。
- 状态码：`200/201` 成功，`400` 参数错误，`401` 未登录，`403` 无权限，`404` 不存在，`409` 状态冲突，`429` 限流，`500` 服务端故障。

推荐契约模板：

```ts
export type ApiSuccess<T> = {
  data: T;
  requestId: string;
};

export type ApiFailure = {
  error: {
    code: "VALIDATION_ERROR" | "UNAUTHORIZED" | "FORBIDDEN" | "NOT_FOUND" | "CONFLICT" | "INTERNAL_ERROR";
    message: string;
  };
  requestId: string;
};

export type CreateAnalysisRequest = {
  input: string;
};

export type Analysis = {
  id: string;
  status: "pending" | "processing" | "completed" | "failed";
  result: string | null;
  createdAt: string;
};

export type CreateAnalysisResponse = ApiSuccess<Analysis> | ApiFailure;
```

接口评审问题：前端是否只需此数据就能渲染？字段是否来自可信服务端？失败时页面能显示什么？刷新后能否根据 `id` 重新取得结果？这四项回答清楚才开始并行编码。

## 5. Git 双人协作指南

### 5.1 规则

1. `main` 永远可运行、可部署。日常开发不直接提交到 `main`。
2. 一项可独立验证的工作对应一个分支和一个 PR。分支格式：`feat/<scope>`、`fix/<scope>`、`docs/<scope>`。
3. 小步提交。提交信息使用 `feat:`、`fix:`、`docs:`、`chore:` 开头，描述完成的结果。
4. 改共享类型、数据库迁移、环境变量、依赖版本前先告知对方；这些是高冲突文件。
5. 合并前运行 `npm run lint` 和 `npm run build`，并由另一人按核心路径测试 Preview。

### 5.2 日常命令速查

```bash
# 获取 main 最新状态，并从其创建新功能分支
git switch main
git pull origin main
git switch -c feat/<scope>

# 查看本次改动，提交并推送
git status
git add <file-or-directory>
git commit -m "feat: <完成的用户价值>"
git push -u origin feat/<scope>
```

发起 PR 时写明：目的、影响的页面/API、如何测试、环境变量/迁移是否变化、当前已知限制。合并后双方执行 `git switch main && git pull origin main`，不要继续在已合并分支上开发下一个需求。

### 5.3 示例一：佟雨泽开发前端页面

目标：按已确定的 `CreateAnalysisResponse` 类型，实现提交页和 Mock 状态。

```bash
git switch main
git pull origin main
git switch -c feat/analysis-form

# 修改 app/(product)/analysis/page.tsx 和 components/analysis-form.tsx
npm run lint
git add app components lib/types
git commit -m "feat: 添加分析提交表单和结果状态"
git push -u origin feat/analysis-form
```

GitHub 中创建 PR。PR 描述说明：页面先使用契约中的 Mock 数据；待 `POST /api/analyses` 就绪后替换请求层。杨思涵在 Preview 中检查加载、成功、失败和空输入四种状态后批准合并。

### 5.4 示例二：杨思涵开发后端并同步主分支

目标：实现 `POST /api/analyses`，并在合并前解决主分支上的类型更新。

```bash
git switch main
git pull origin main
git switch -c feat/analysis-api

# 新增 app/api/analyses/route.ts 与 lib/services/analysis-service.ts
npm run lint
npm run build
git add app/api lib package.json package-lock.json
git commit -m "feat: 提供分析创建接口"
git push -u origin feat/analysis-api
```

若此时 `main` 已更新，不要在 PR 页面盲目解决冲突：

```bash
git fetch origin
git rebase origin/main
# 逐个解决冲突，确认共享 API 类型仍符合双方约定
npm run lint
npm run build
git push --force-with-lease
```

只对自己的功能分支使用 `--force-with-lease`，绝不对 `main` 使用强推。若冲突涉及 `lib/types/`、SQL 或接口字段，先停止并与佟雨泽确认契约，再继续 rebase。
