# 第二阶段方案设计：个人中心与意外发现

## 2026-08-22 个人中心升级与今日开发计划

## 1. 背景与现状

第一阶段已经完成资源目录、搜索、资源详情、登录、收藏和个人书架的基础闭环。当前 `/library` 页面主要包含登录表单、收藏资源列表、移除收藏和退出登录，能够完成 P0 验收，但还不能承担用户回访、阅读沉淀和第二阶段探索的入口职责。

已有能力可以复用：

- `profiles` 表已经存在；当前收藏接口会在首次访问时初始化，但第二阶段的 profile service 也必须独立负责初始化；
- `saved_resources` 已支持 `note`、`saved_at`，并有 RLS；
- `ResourceRelation` 类型和 `resource_relations` 表已经为“意外发现”预留；
- 当前技术栈继续使用 Next.js 16 App Router、Supabase、Route Handler、Zod 和 Tailwind，不新增 UI 或数据服务依赖。

## 2. 本阶段目标

今天完成一个可演示的第二阶段增量：

1. 将个人书架升级为“个人中心 / 我的阅读档案”，让用户能看到自己的阅读状态、收藏线索和下一步行动。
2. 在个人中心提供“带我偏离一点”入口；资源详情页入口列为 P1，可在主链路稳定后接入。
3. 基于人工维护的 `resource_relations` 返回有解释的跨主题推荐，保证没有 AI 时主流程也可用。
4. 为后续 AI 解释保留接口边界，但今天不把模型调用作为主链路依赖。

本阶段不做真实借书、还书、座位预约、门禁、实时馆藏、管理员后台或社交关系。这些功能需要独立的业务模型和并发规则，不应混入当前产品主线。

## 3. 产品定位

个人中心不是传统图书馆管理后台，而是用户的“阅读轨迹工作台”。页面要回答三个问题：

- 我是谁，最近在读什么？
- 我保存了哪些值得回看的线索？
- 下一步可以从哪里偏离，发现什么意外连接？

建议保留 `/library` 作为兼容入口，同时在页面标题和导航中使用“个人中心”或“我的阅读档案”。不立即改成新路由，避免破坏现有链接和验收脚本。

## 4. 页面方案

### 4.1 页面结构

`/library` 页面从单列书架调整为以下结构：

```text
顶部导航
  个人头像/显示名      找资源      我的书架

个人中心头部
  显示名、邮箱、账号注册时间（能读取时展示）
  一句阅读状态文案
  [继续探索] [退出登录]

阅读概览
  已收藏资源数    最近收藏时间    覆盖主题数

探索入口
  “带我偏离一点”按钮
  推荐理由和 1-3 条候选资源

我的书架
  全部 / 有笔记 / 在线可读 / 待查馆藏
  资源卡片、标签、收藏笔记、收藏时间
  移除收藏

空态或错误态
```

### 4.2 个人资料

今天只做轻量资料展示和显示名编辑，不做头像上传和复杂账户设置：

- 显示名默认取邮箱 `@` 前的部分，且只在 `profiles.display_name IS NULL` 时写入；
- `/api/profile` GET 必须先确保 profile 存在，再读取资料；读取资料不能覆盖用户已经编辑过的显示名；
- 用户可编辑 1-50 个字符的显示名；
- 邮箱只读展示；
- 保存失败时保留输入内容并显示错误；
- 资料保存使用已有 `profiles` 表和 RLS。

### 4.3 阅读概览

统计直接从当前用户收藏查询计算，避免今天新增统计表。`/api/profile` 返回 profile 和初始 stats，`/api/saved-resources` 单独返回书架；两次请求之间允许短暂不一致，前端在书架请求成功后以书架响应重新计算并覆盖统计展示：

- `savedCount`：收藏资源数；
- `topicCount`：收藏资源涉及的去重标签数；
- `latestSavedAt`：最近一次收藏时间；
- `notedCount`：有个人笔记的收藏数。

这些统计属于展示数据，不作为推荐算法的唯一依据。

### 4.4 书架分区

使用前端筛选，不立即引入数据库分类字段：

- 全部：所有收藏；
- 有笔记：`note` 非空；
- 在线可读：`availability = online`；
- 馆藏待查：`availability = check_library`。

筛选状态应保留在 URL，例如 `/library?view=noted`，刷新后不丢失当前视图。

### 4.5 意外发现卡片

每次进入个人中心显示一个确定性推荐入口：

- 优先以最近收藏资源作为 source；
- 查询其 `unexpected_bridge` 关系；
- 没有意外连接时回退到 `same_theme`；
- 最多展示 3 条候选；
- 每条候选必须展示关系类型和 `explanation`；
- 点击资源后可继续查看详情并再次偏离。

按钮文案统一为“带我偏离一点”，推荐文案示例为“从创造力走向认知心理学：换一个角度看创作”。

## 6. 接口设计

### 6.1 获取个人资料与概览

接口名称：获取当前用户资料

请求方式：`GET`

请求路径：`/api/profile`

响应数据：

```ts
type ProfileOverview = {
  profile: {
    id: string;
    displayName: string | null;
    email: string;
    joinedAt: string | null;
  };
  stats: {
    savedCount: number;
    notedCount: number;
    topicCount: number;
    latestSavedAt: string | null;
  };
};
```

未登录返回统一的 `401 UNAUTHORIZED`；数据库错误不得把 Supabase 原始错误返回给浏览器。

`joinedAt` 取 `auth.users.created_at`，表示账号注册时间；不得把 `profiles.created_at` 命名为加入时间。若当前 adapter 无法读取该字段，则返回 `null`，页面不显示该项。

GET/PATCH 的处理都必须先执行同一个 `ensureProfile` 流程：验证当前用户 -> 查询 profile -> 不存在时按邮箱前缀创建默认 profile（`insert ... on conflict do nothing`）-> 对已存在但 `display_name IS NULL` 的 profile 执行 `update profiles set display_name = :email_prefix where id = :user_id and display_name is null` -> 重新读取 profile。该流程不能覆盖用户已经编辑过的显示名。GET 随后计算 stats；PATCH 再执行显示名更新。这样客户端即使绕过 GET 直接 PATCH，也不会因为 profile 尚未创建而失败。

### 6.2 更新显示名

接口名称：更新当前用户资料

请求方式：`PATCH`

请求路径：`/api/profile`

请求体：

```json
{ "displayName": "新的显示名" }
```

校验规则：去除首尾空格，长度 1-50；空值不允许作为显示名提交。只允许更新当前用户自己的 profile。

### 6.3 获取意外发现

接口名称：获取下一条阅读偏离

请求方式：`GET`

请求路径：`/api/discover`

可选参数：`sourceResourceId`。不提供时使用当前用户最近收藏的资源。

权限和参数语义：

- 带 `sourceResourceId` 时，允许未登录用户对公开资源进行发现；source 不要求属于当前用户；
- 不带参数时，必须登录，并从当前用户最近收藏中选择 source；未登录返回 `401 UNAUTHORIZED`；没有收藏返回 `200` 的 `mode: "empty"`；
- `sourceResourceId` 必须是合法 UUID，非法值返回 `400 VALIDATION_ERROR`；
- source 不存在或不可公开读取时返回 `404 RESOURCE_NOT_FOUND`；
- 推荐结果只来自公开资源，排除 source 自身；
- 响应设置 `Cache-Control: no-store`，避免把用户个性化结果缓存到共享缓存。

响应数据：

```ts
type DiscoveryData = {
  source: ResourceListItem | null;
  items: Array<ResourceListItem & {
    relationType: RelationType;
    explanation: string;
    strength: number;
  }>;
  mode: "unexpected_bridge" | "same_theme" | "empty";
};
```

没有收藏时返回 `items: []`、`mode: "empty"`，页面显示“先收藏一条线索，再从它偏离”。

### 6.4 暂不新增的接口

今天不新增借阅、座位、预约、管理员和实时馆藏接口。AI 接口也暂不作为必需接口，后续可在 `/api/discover/explain` 增加受限的解释能力。

## 7. 数据模型与迁移

### 7.1 今天需要的数据库变更

新增 migration，而不是修改已经执行过的旧 migration：

- 为 `profiles.display_name` 保持现有约束；
- 如需补充 `bio`，今天不建议新增，避免扩大资料编辑范围；
- 为 `resource_relations` 增加/补齐三条测试故事的 `unexpected_bridge` 种子数据；
- 新增 migration 创建 `resource_relations_source_type_strength_idx`，覆盖 `(source_resource_id, relation_type, strength desc)`；不能只依赖现有的 `(source_resource_id, strength desc)` 索引。

关系种子最低标准：

| 起点故事 | `unexpected_bridge` | `same_theme` 回退 |
|---|---:|---:|
| AI 与创造力 | 每个起点至少 2 条 | 至少 1 条 |
| 城市与记忆 | 每个起点至少 2 条 | 至少 1 条 |
| 偶然阅读 | 每个起点至少 2 条 | 至少 1 条 |

关系 seed 文件必须使用唯一约束配合 `ON CONFLICT DO UPDATE` 或 `DO NOTHING`，保证可重复执行。执行顺序为：先在 Preview 验证 migration 和 seed，再由同一版本迁移到 Production，并记录执行时间和版本。

### 7.2 不新增统计表的理由

当前收藏量和主题数可以从个人收藏列表计算。用户规模较小时新增 `reading_stats` 会增加迁移、同步和一致性成本，暂不值得；最终 UI 统计以书架响应为准，以消除 profile 初始 stats 与书架列表的竞态。

### 7.3 类型与 Schema

建议在 `lib/types/resources.ts` 增加 `DiscoveryData` 和 `ProfileOverview`，在 `lib/schemas/resources.ts` 或新增 `lib/schemas/profile.ts` 增加 profile body 校验。接口统一使用 `lib/types/api.ts` 的成功/失败信封。

## 11. 风险与取舍

| 风险 | 处理方式 |
|---|---|
| profile 接口增加网络请求导致页面变慢 | 首屏先渲染骨架，资料与书架并行请求；失败时保留书架内容 |
| 关系种子不足导致推荐空白 | 每个故事起点至少 2 条 unexpected_bridge 和 1 条 same_theme 回退关系 |
| 统计与收藏列表不一致 | profile 返回初始 stats；书架请求成功后前端以书架响应重新计算最终展示，不建立异步统计表 |
| AI 调用超时或额度不足 | 确定性关系推荐作为主链路，AI 只做后续增强 |
| 个人中心范围膨胀 | 今日明确不做头像上传、阅读进度、社交、借阅和座位预约；详情页入口和体验打磨降为 P1 |

## 12. 下一步

本方案确认后进入代码实现阶段。实现顺序必须是：先迁移与类型，再 service/API，再个人中心 UI，最后接通发现入口和验收。若实现过程中需要新增字段或修改现有 API，先提交契约变更提议并获得双方确认。
